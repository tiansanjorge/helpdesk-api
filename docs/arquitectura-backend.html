Parte A · Cómo está armado el código

Lo que ocurre dentro de la API desde que entra un request hasta que se toca la base.

A1 · Módulos e inyección de dependencias

NestJS agrupa el código en módulos. Cada módulo reúne un controller, un service y lo que necesite. Nadie construye sus dependencias a mano: el service declara lo que necesita en el constructor y Nest se lo entrega. Eso es la inyección de dependencias. En espíritu se parece a un Provider de React: alguien provee, quien necesita pide.

@Injectable()
export class TicketsService {
  constructor(private readonly prisma: PrismaService) {}   // Nest lo entrega
}

Para llevar a la clase

  • ¿Qué problema resuelve la inyección de dependencias frente a hacer new PrismaService() dentro del service? (pista: tests)
  • ¿Qué diferencia hay entre providers, imports y exports de un módulo?
  • ¿Por qué conviene una sola instancia de PrismaService (una sola conexión al pool) y no una por request?

A2 · El camino de un request

Cada request atraviesa una cadena de etapas en un orden fijo. Si una etapa falla, la cadena se corta y el error sale por el filtro de excepciones. En NestJS el orden real es: middleware, guards, interceptors, pipes, controller/service, y los filtros al final. Por eso los guards corren antes que la validación.

Para llevar a la clase

  • ¿Qué diferencia hay entre 401 y 403? ¿Y entre 400, 404 y 409?
  • ¿Por qué el controller no debería tener lógica de negocio?
  • ¿Qué es un DTO y por qué se valida en el borde y no dentro del service?
  • ¿Qué hace un interceptor y en qué se diferencia de un guard?

A3 · Login y cookie httpOnly

El login verifica la contraseña contra un hash (nunca se guarda la contraseña), firma un JWT con la identidad y el rol, y lo entrega en una cookie que JavaScript no puede leer. Desde ahí el navegador la adjunta solo en cada request.

Dos cosas para tener presentes. (1) Un JWT ya emitido sigue siendo válido hasta que vence, aunque después desactives al usuario con isActive = false: hay que decidir cómo se maneja (vencimiento corto, chequeo en cada request, etc.). (2) Si el front (Vercel) y la API (AWS) quedan en sitios distintos, el navegador trata la cookie como de terceros: haría falta SameSite=None; Secure, CORS con credenciales y fetch(..., { credentials: 'include' }), y aun así muchos navegadores las bloquean. Lo más limpio suele ser servir ambos bajo el mismo dominio (por ejemplo app.tudominio.com y api.tudominio.com). Lo tengo como punto a verificar al integrar el front.

Para llevar a la clase

  • ¿De qué ataque protege HttpOnly y de cuál no?
  • ¿Qué es CSRF y cómo ayuda SameSite?
  • ¿Qué es un salt y por qué se usa bcrypt o argon2 en vez de SHA-256?
  • ¿Qué contiene un JWT, quién puede leerlo y qué garantiza la firma?

A4 · Dónde vive el filtro por organización

El aislamiento entre organizaciones depende de que toda query filtre por el organizationId del usuario logueado. Ese dato viaja siempre en la misma cadena y nunca sale del body ni de la URL.

JWT firmado→ req.user.organizationId→ parámetro del service→ where de Prisma
Opción 1 · Explícito en cada query
findOne(user: AuthUser, id: string) {
  return this.prisma.ticket.findFirst({
    where: { id, organizationId: user.organizationId },
  });
}
  • Se lee y se depura fácil.
  • Depende de no olvidarse en ninguna de las decenas de queries.
Opción 2 · Centralizado (ilustrativo)
// cliente "atado" a una organización
const db = this.tenantDb.for(user.organizationId);
return db.ticket.findFirst({ where: { id } });
// el filtro se agrega solo
  • No se puede olvidar el filtro.
  • Más "magia": cuesta más entender qué SQL sale realmente.

La opción 2 es un pseudocódigo: la forma concreta (por ejemplo una extensión del cliente de Prisma) se elige en la Fase 2 con casos reales. Sea cual sea, un test que intente leer datos de otra organización tiene que fallar siempre.

Para llevar a la clase

  • ¿Qué es un IDOR? ¿Por qué un UUID no lo resuelve por sí solo?
  • Si el ticket es de otra organización, ¿devolvés 403 o 404? ¿Qué filtra cada opción?
  • ¿Qué pasaría si aceptáramos el organizationId desde el body?
  • ¿Qué agregaría Row-Level Security de Postgres frente a las dos opciones?

A5 · Transacciones y concurrencia

Crear un ticket toca tres cosas: el contador de la organización, el ticket y el historial. O pasan las tres o ninguna: es una transacción. Además, dos agentes pueden crear tickets a la vez: el bloqueo de fila hace que uno espere al otro y nunca reciban el mismo número.

Para llevar a la clase

  • ¿Qué significa ACID? ¿Cuál de las cuatro letras evita que A deje el contador a medias?
  • ¿Qué pasa si el servidor se cae entre el INSERT y el COMMIT?
  • ¿Por qué sigue siendo útil el índice único (organizationId, number) aunque exista el bloqueo? (defensa en profundidad)
  • ¿Qué costo tiene un bloqueo de fila? ¿Cuándo se vuelve un cuello de botella?

Parte B · Del código a la nube

Cómo el esquema llega a producción, cómo se mueven los archivos y los trabajos en segundo plano, y dónde corre cada pieza.

B1 · Migraciones

Una migración es un archivo SQL versionado que lleva la base de un estado al siguiente. Se commitea junto con el código, así cualquier entorno puede reconstruir el esquema aplicando las migraciones en orden.

Para llevar a la clase

  • ¿Qué pasa si editás una migración que ya se aplicó en otro entorno?
  • ¿Qué es el "drift" entre el schema y la base real?
  • ¿Cómo se hace un cambio que rompe datos (renombrar o borrar una columna) sin downtime?
  • ¿Qué diferencia hay entre migrate dev y migrate deploy?

B2 · Adjuntos en S3 con URL prefirmada

Los archivos no pasan por la API ni se guardan en la base: van directo del navegador a S3 con una URL prefirmada, un permiso temporal que la API firma. En Postgres queda solo la metadata y la storageKey.

Para llevar a la clase

  • ¿Por qué no subir el archivo a través de la API? ¿Qué se gana y qué se complica?
  • ¿Qué es exactamente una URL prefirmada y por qué vence?
  • ¿Qué pasa si el usuario sube el archivo pero nunca confirma? (archivos huérfanos)
  • ¿Qué es un rol IAM y cómo evita poner claves de AWS en el código?

B3 · Trabajo asíncrono con SQS y Lambda

Mandar un email no tiene por qué demorar la respuesta al usuario. La API publica un mensaje en una cola y responde; una función Lambda lo procesa después. Si falla, el mensaje se reintenta y, tras varios fallos, va a una cola de mensajes muertos.

Para llevar a la clase

  • ¿Qué significa que un consumidor sea idempotente y por qué importa con reintentos?
  • ¿Qué es una dead-letter queue y quién mira lo que cae ahí?
  • ¿Qué es el patrón outbox y qué problema resuelve?
  • ¿Cuándo un proceso debe ser asíncrono y cuándo es mejor hacerlo en el mismo request?

B4 · Despliegue en AWS

La API se empaqueta en una imagen Docker, se guarda en ECR y corre en ECS Fargate detrás de un balanceador. Los secretos y los permisos no van en el código: los entregan Secrets Manager y roles de IAM. La base queda en Neon, fuera de AWS.

Para llevar a la clase

  • ¿Qué es un contenedor y en qué se diferencia de una máquina virtual?
  • ¿Qué es una VPC, una subred pública y un security group?
  • ¿Qué diferencia hay entre un usuario IAM y un rol IAM?
  • ¿Qué significa escalar horizontalmente y qué de la API tiene que ser stateless para poder hacerlo?

B5 · Estrategia de testing

Tres niveles con distinto costo. Para este proyecto el peso está en los tests de integración: son los que prueban lo que más nos importa (autenticación, permisos, aislamiento y transacciones) con una base real.

Para llevar a la clase

  • ¿Qué se mockea y qué no? ¿Qué se pierde cuando mockeás la base?
  • ¿Qué hace que un test sea frágil?
  • ¿Cómo se prueba una condición de carrera como la del contador de tickets?
